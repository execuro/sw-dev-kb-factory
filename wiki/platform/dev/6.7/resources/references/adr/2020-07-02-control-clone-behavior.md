## What it is

Architecture decision record (2020-07-02) on how a developer controls whether an entity association is copied when the entity is cloned. Clone behavior is driven by the `Shopware\Core\Framework\DataAbstractionLayer\Field\Flag\CascadeDelete` flag: associations carrying it are cloned, and an optional constructor parameter disables this per association.

## When to use

- You define an entity association that has `CascadeDelete` (so child rows are deleted with the parent) but whose data should not be duplicated when the parent is cloned — e.g. data regenerated by an indexer, or data the administration overwrites anyway.
- You are debugging why an association is or is not present on a cloned entity.

## Key steps / config

1. Add `CascadeDelete` to the association as usual; the constructor argument `cloneRelevant` defaults to `true`.
2. Pass `false` to keep cascade deletion but exclude the association from cloning:

```php
(new OneToManyAssociationField('searchKeywords', ProductSearchKeywordDefinition::class, 'product_id'))
    ->addFlags(new CascadeDelete(false)),
```

During cloning, the version manager skips every association field that has no `CascadeDelete` flag or whose flag returns `false` from `isCloneRelevant()`. Many-to-one associations are always skipped, since they are not part of the root entity.

Associations in core flagged `new CascadeDelete(false)` by this decision:

- `product.productReviews` — overwritten by the administration anyway
- `product.searchKeywords` — rebuilt by the product indexer
- `product.categoriesRo` — rebuilt by the product indexer

## Essential identifiers

- `Shopware\Core\Framework\DataAbstractionLayer\Field\Flag\CascadeDelete`
- `CascadeDelete::$cloneRelevant` (constructor parameter, default `true`)
- `CascadeDelete::isCloneRelevant()`

## Gotchas

- An association without `CascadeDelete` is never cloned; the flag couples delete and clone semantics.

## Version notes

- The source states the `cloneRelevant` control became available after the 6.3 release.
