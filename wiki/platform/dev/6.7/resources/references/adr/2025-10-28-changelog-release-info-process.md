## What it is

An architecture decision record (2025-10-28) that supersedes the 2020 changelog ADR and replaces the per-change markdown changelog workflow with two curated, in-repository files for developer-facing release information, complemented by an automatically generated raw changelog.

## When to use

- You open a pull request against the Shopware repository and must decide where to document a developer-facing change or a breaking change.
- You look for release notes or upgrade instructions of a Shopware minor/major version.

## Key steps / config

Old workflow (superseded): one markdown file per change under `/changelog/_unreleased`, aggregated by a build step into `CHANGELOG.md` and `UPGRADE.md`. It caused duplication, lacked high-level developer context and kept release notes in a separate repository.

New curated in-repo model:

- `RELEASE_INFO-6.<currentMajor>.md` — developer-facing release notes with one section per minor version; new entries go into the "Upcoming" section.
- `UPGRADE-6.<upcomingMajor>.md` — upgrade instructions and breaking changes.

Skeleton of a `RELEASE_INFO-6.7.md` entry (category, concise description, PR reference):

```markdown
## 6.7.5 (Upcoming)
### Core
- <concise description> (PR #<number>)
### Administration
- <concise description> (PR #<number>)
```

An `UPGRADE-6.8.md` entry is a heading naming the change, followed by what changed and how plugins should adjust (sub-headings such as "What changed"/"How to adjust" are optional).

Rules for PR authors and reviewers:

1. Information useful to external developers goes into `RELEASE_INFO-6.X.md`; breaking changes go into `UPGRADE-6.Y.md`.
2. CI does not enforce a strict entry format initially; reviewers check consistency and readability and ensure entries are added or explicitly marked unnecessary.
3. The PR template references this process with checklist guidance.
4. CI will later validate that `RELEASE_INFO` or `UPGRADE` was updated when relevant (or explicitly skipped with justification).

Raw changelog: generated automatically per release from merged PRs and commits, grouped by labels (`bug`, `feature`, `performance`), with links to PRs and authors; intended for engineering, support and partners, and linked from the release notes.

## Essential identifiers

- `RELEASE_INFO-6.<currentMajor>.md`, `UPGRADE-6.<upcomingMajor>.md`
- `/changelog/_unreleased`, `CHANGELOG.md`, `UPGRADE.md` (old workflow)
- `adr/_superseded/2020-08-03-implement-new-changelog.md`

## Gotchas

- Marketing and Comms take content only from `RELEASE_INFO` and `UPGRADE`, never from the raw changelog; internal documentation links to these two files as the single source of truth.
- The ADR's example entries are illustrative only: a `CartRoute` parameter `guestLogin` and a `ContextResolverInterface` replacement do not exist in 6.7.15.1. The example's `SalesChannelContextSwitcher` deprecation is real, but the installed code points to `AbstractContextSwitchRoute` as the replacement.
- The superseded ADR is kept under `adr/_superseded/` for historical reference.
