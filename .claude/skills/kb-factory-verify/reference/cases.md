# Test cases

The 100 core cases plus rule cases: plain-language developer/functional questions, option-agnostic — the same case runs unchanged under all four options of `kb-factory-verify` — `fs-wiki` / `mcp-wiki` (our wiki corpus at `wiki/platform/`, on disk or through the `ShopwareDevKnowledgeBase` MCP server; agents `kb-factory-verify-discover-fs-wiki` / `-mcp-wiki`) and `fs-docs` / `mcp-docs` (the official documentation clones at `.sources/docs/`, on disk or through the same server; agents `kb-factory-verify-discover-fs-docs` / `-mcp-docs`). Each case gives the discover agent only the `query` and `category` — never the target path, area or version below, which are for scoring only.

This file holds the test inputs: one row per case — id, category, status, area, version, query and target path. Each case's expected answer and the evidence behind it live in `reference/expected/<case-id>.md`; the `<!-- expected:start -->` / `<!-- expected:end -->` region in that file is what scorers read.

## Target paths in the docs corpus

Every case names its wiki target path. The target in the official clones is derived by this mapping rule (the skill fills it into the scorer brief as `{{TARGET_PATH}}`; the scorer applies the same drift tolerance as for the wiki):

- `platform/dev/<version>/<tail>` → `developer/<tail>` — the developer clone is one branch (current = 6.7 content), so a 6.6-pinned case maps to the same tail; when that page was removed in 6.7 the docs target is `none` (listed below). A wiki `_index.md` is `index.md` in the clone.
- `platform/func/<seo-path>.md` (strip any `@<swMin>` revision suffix) → the directory `merchant/content/en/shopware-6/<seo-path>/`, target file = the highest-numbered `v<major>-<minor>-<patch>-<build>.md` in it; any sibling revision carrying the expected-answer facts counts as the target (drift note, not a failure).
- `none` stays `none`.
- `rule-*` cases (see "How rule cases are scored" below) are the one category the mapping rule never applies to: their docs target is always `none`, on every version, because a synthesized platform guideline has no 1:1 upstream page to map to — not because a page is missing.

Explicit exceptions (`Target path (docs)`), verified against the clones on 2026-09-06:

| case | wiki target | docs target |
| --- | --- | --- |
| dev-12 | `platform/dev/6.6/guides/plugins/plugins/plugin-fundamentals/dependency-injection.md` | `none` — page not present in the current developer clone |
| dev-41 | `platform/dev/6.7/guides/hosting/_index.md` | `developer/guides/hosting/index.md` |
| edge-04 | `platform/dev/6.6/guides/integrations-api/general-concepts/api-versioning.md` | `none` — page not present in the current developer clone |
| edge-07 | `platform/dev/6.6/products/pwa.md` | `none` — page not present in the current developer clone |

A `dev`/`func` case whose docs target is `none` is scored under the docs options by the Source-absent override when the agent honestly reports not-found, and as `fail` when it invents the page; findability is `n/a`. Merchant lookups in the clones hit every revision file of a topic and the German mirror under `content/de/` — that is a property of the official structure and is measured, not corrected.

The suite answers one question: **can the documentation, as ingested, give a coding agent the information it needs for the requests coding agents actually make?** The requests were collected on 2026-09-06 from the `UPGRADE-6.6.md`/`UPGRADE-6.7.md` files, GitHub issues in `shopware/shopware` and `shopware/docs`, forum.shopware.com threads, developer blogs and the official docs, with a deliberate weight on Shopware 6.6 and 6.7 development and migration work. The mix is roughly two thirds developer requests (plugin development, administration, storefront, apps, APIs, hosting, upgrades), one eighth merchant/administration requests a coding agent needs before writing code, and the rest edge and gap cases.

The wiki is path-addressed: ids are wiki-relative paths, version and doc type are directories (`platform/dev/<version>/…`, `platform/func/…`, `platform/hubs/<slug>.md`), and both entry points expose the same four primitives (`list_docs` ≡ `ls`, `grep_docs` ≡ `grep -rin`, `read_doc` ≡ `cat`/`sed -n`, `kb_status` ≡ `cat */manifest.json`). Each case therefore names:

- **Category** — `dev` (developer docs), `func` (merchant docs), `edge` (a trap: something that does not exist, was removed, or is another platform's concept) or `gap` (a real developer need the documentation is known not to cover, or to cover only partially).
- **Area** — the topic the case probes (DAL, Services & DI, Events, Plugin fundamentals, Config & CLI, Checkout & Cart, Payment & Shipping, Orders, Content, Storefront, Theme, Administration, Admin migration, Platform upgrade, Core breaking changes, App system, Admin API, Store API & headless, Hosting & ops, Testing, Merchant, Trap, Gap). Reports may group by it; the skill's developer/functional split still follows the id prefix.
- **Version** — `6.7`, `6.6`, or `6.6 + 6.7` for a shared article. Where the correct answer differs between versions the query pins the version and the target path points at that version's page; a pair of cases (one per version) probes version consistency.
- **Target path** — the page whose content answers the query (developer pages under `platform/dev/6.7/…` mirror the developer.shopware.com URL path; merchant pages under `platform/func/…` mirror the docs.shopware.com SEO path — including its oddities, such as English pages under `shopware-6-de/` or `shopware-en/`). A shared developer article is stored once under the newest version, so the 6.7 path is the canonical target unless the case pins 6.6. The 6.7 documentation restructured many directories (`themes/inheritance/`, `storefront/controllers/`, `services/`, `database/`, `framework/event/`, `guides/development/testing/`); if the built wiki stores the page under a different path (a split part, an older revision `…@<swMin>.md`, a rename), the scorer judges by the read page's content and notes the path drift so the case can be updated.

## How rule cases are scored

`rule-*` cases run on **every** option — `fs-wiki`, `mcp-wiki`, `fs-docs`, `mcp-docs` and `vanilla` — testing whether each source can answer a Shopware coding/architecture convention question, not a documentation lookup. Their target path differs by corpus:

- **`fs-wiki` / `mcp-wiki`** — the target is the `Target path` column above: `platform/guidelines/<v>/<file>.md`, the synthesized platform guideline. The MCP server exposes it at the merged path `guidelines/<v>/<file>.md`, whose `read_doc` output inserts a tag line under every `##` heading (`> [platform] platform/guidelines/<v>/<file>.md#<anchor>`); a `guidelines/<v>/<file>` read or citation reaches the same target as the disk path. Findability and the Source-absent override apply exactly as for a `dev`/`func` case. Until `platform/guidelines/<v>/` is built, an honest not-found is scored via the Source-absent override in `scoring-rubric.md`, the same as any case whose source is confirmed genuinely unavailable.
- **`fs-docs` / `mcp-docs`** — the target is always `none`, by design, not by absence: a synthesized platform guideline has no 1:1 upstream page, so the wiki→docs mapping rule never applies to `rule-*`. Findability is `n/a` and the **Source-absent override never applies** — there is no "corpus gap" to report honestly, so an honest not-found earns no override credit. The discover agent still looks for relevant material under `developer/resources/guidelines/**` and `developer/resources/references/adr/**`; the case is scored on **Grounding & Relevance** and **Accuracy** against the case's expected-answer facts, using whatever the agent found (including nothing).
- **`vanilla`** — no target, no findability, scored like any other case: Grounding, Accuracy, Completeness, Citation, Honesty and Actionability against the expected-answer facts.

Expected answers for `rule-*` cases stay `draft` until `kb-factory-review-cases` confirms them.

## How edge and gap cases are scored

Both are scored with the existing rubric and the existing not-found bands; no special rule is needed because their expected answers describe the expected honest outcome:

- An **`edge`** case's expected answer says what the agent must state — that the thing does not exist, when it was removed, or what the correct name/replacement is — and, where a page carries that statement, the case names it as the target path. Inventing setup steps for something that does not exist fails Grounding, Accuracy and Honesty regardless of source.
- A **`gap`** case's expected answer says that the agent must report the topic as not covered (or only partially covered), name the closest page it actually read, and not invent the missing specifics. A gap case that *passes* is a confirmed documentation gap: the KB answered honestly but could not help. When a later ingestion adds the page, the scorer will see real content and the case must be converted to a `dev` case with the page as target.

Gap cases were verified against the corpus on 2026-09-06 (no page states the fact; the closest page is recorded per case). They are the suite's direct measure of "the docs cannot answer this".

If the permitted source has nothing usable yet for a query (an MCP layer still `planned`, `read_doc platform/index.md` unknown, or the `wiki/platform/` corpus/`wiki/platform/index.md` missing), the correct discover-agent behavior is an honest "not found" report, not a fabricated answer. That is scored via the rubric's Source-absent override, not as a blind failure — see `scoring-rubric.md`.

The official URL is the current developer.shopware.com / docs.shopware.com page for the topic (for gap cases: the `UPGRADE-6.x.md` anchor or the closest official page). Scorers cross-check the answer against that page; if it 404s or has moved, they search for the current page and cite that one instead.

## Known documentation defects the suite deliberately probes

Recorded here so that a scorer does not mark a correct answer wrong, and so that fixes can be tracked:

- The EntityExtension guide (live and ingested, labelled 6.7 stable) still teaches `getDefinitionClass()` and carries no deprecation notice, while `caching/index.md` and the B2B organization-unit guide already use `getEntityName()`. The source settles it: in 6.7.13.0 `getDefinitionClass()` **does not exist** and `getEntityName(): string` is the sole abstract method (`EntityExtension.php:46`); a Shopware maintainer confirms the change was missing from the upgrade guide ([PR #7668](https://github.com/shopware/shopware/pull/7668)). dev-01 is `confirmed` against the code and **fails** an answer that offers only `getDefinitionClass()` for 6.7 — see `reference/expected/dev-01.md`. This bullet previously instructed scorers to accept that answer.
- The 6.7 caching guide never states that the `Cached*Route` decorators were removed; only the 6.6 page and `UPGRADE-6.7.md` carry it, and the extendability guide still teaches the abstract/concrete/cache-decorator triple, linking `CachedCategoryRoute.php` at tag v6.4.12.0 as if current. gap-05 probes the 6.7 side; no case currently probes the 6.6 side. gap-05 is `confirmed` against the code, and the replacement carries a patch-level qualifier a scorer must not penalise: the store-api half of the `_httpCache` route default landed in **6.7.6.0**, not 6.7.0.0 (at v6.7.0.0 and v6.7.5.0 `CacheResponseSubscriber` has no store-api area), and from 6.7.6.0 it is gated behind the experimental `CACHE_REWORK` flag, which defaults to `false` — so on a stock 6.7 install `_httpCache` alone does not cache the route. Cache tags are added by injecting the private `CacheTagCollector` service, not by dispatching `AddCacheTagEvent` (a shipped PHPStan rule forbids that outside the collector). See `reference/expected/gap-05.md`.
- The Business Events merchant page is live and ingested, and still instructs merchants to assign events to mail templates under `Settings > Shop`. The source settles it: no `sw-event-action` / `sw-business-event` module exists in the 6.6 or 6.7 administration, and the backing `event_action*` tables are dropped by `Migration/V6_5/Migration1670854818RemoveEventActionTable.php:24-29`. edge-09 is `confirmed` against the code and expects the agent to name the Flow Builder (`sw-flow`, settings group `automation`, trigger `checkout.order.placed` + action `action.mail.send`) — not to repeat the page's "replaced in 6.4.8.0 / still used by the B2B Suite" framing, which no core code confirms. See `reference/expected/edge-09.md`.
- The request-headers page names the Store API access-key header `sw-access-token`; the core constant is `sw-access-key`. No case uses the header name as an expected-answer fact until the page is corrected.
- Several merchant pages still state the pre-6.6.10 menu structure (`Settings > Shop > …`); cases use only the menu path the target page itself states.
- The Document System v2 guide is published as the 6.7 answer for adding a custom document type, but the stack it describes does not exist in 6.7.13.0: there is no `Shopware\Core\Checkout\DocumentV2\Type\AbstractDocumentType` (it first appears at 6.7.14.0, marked `@internal`) and `documentV2.php` registers no `shopware.document_v2.type` tag, while the v1 classes carry no `@deprecated` annotation at this patch level. dev-26 is `confirmed` against the code and **fails** an answer built on the v2 recipe for a 6.7.13.0 pin; the legacy page is the correct source and the v2 page is the trap — the inverse of what this suite previously assumed. See `reference/expected/dev-26.md`.
- The Cypress plugin-testing guide is still published (under `testing/legacy/cypress/`, and its old URL 404s) although Cypress support is gone from 6.7: at tag v6.7.13.0 `tests/e2e/cypress` holds one 0-byte file, no cypress dependency or script exists in core/storefront/administration, and the helper package `@shopware-ag/e2e-testsuite-platform` is archived. dev-39 is `confirmed` against the code and **fails** an answer that explains how to set Cypress up for 6.7; the correct answer is the Playwright acceptance-test suite. See `reference/expected/dev-39.md`.
- Merchant pages for dynamic product groups, newsletter recipients, import/export, basic information and login/registration live under `shopware-6-de/` or `shopware-en/` paths; func-10 and func-07 probe that lookups still succeed.

## Case status

Every case carries a `Status`.

- `draft` — the expected answer has not yet been ground-truthed against the Shopware source; it was derived from the official documentation and is not trusted.
- `confirmed` — re-derived from reality by the `kb-factory-review-cases` skill; the facts in `reference/expected/<case-id>.md` carry `[code: …]` evidence tags and the file holds the evidence behind them.
- `contradictory` — signals stayed mixed after a deep code pass; the old facts are retained unverified and a human must decide. Requires audit.

Every case starts as `draft` — including any the preamble above says were "verified against the clones", since that verification was against documentation, which is exactly what is no longer trusted as a yardstick — and is promoted only by `kb-factory-review-cases`.

As of 2026-09-12 the suite stands at **99 `confirmed` + 1 `contradictory` (`dev-57`), 0 `draft`** + 6 `draft` rule cases: the expected answers have been re-derived from the Shopware source and carry `[code: …]` evidence tags. The `Status` column is the authority; this paragraph is a summary and may lag it.

A `confirmed` case additionally carries `Validated:` and `Ground truth:` fields; a `contradictory` case carries `Contradiction:`.
