**Query:** How do I add a custom document type such as a pro-forma invoice in Shopware 6.7?

**Expected answer — every fact an answer must contain:**

1. On 6.7.13.0 the custom type is added through the legacy stack: a class extending `Shopware\Core\Checkout\Document\Renderer\AbstractDocumentRenderer` implementing `supports()` (returns the technical name), `render()` (returns a `RendererResult`) and `getDecorated()`, registered under the service tag `document.renderer` — which autoconfiguration adds automatically to any subclass — and dispatched by `DocumentRendererRegistry` matching `supports()` against the requested type. The Document v2 recipe does not apply at this patch level: `Shopware\Core\Checkout\DocumentV2\Type\AbstractDocumentType` and the tag `shopware.document_v2.type` do not exist in 6.7.13.0 (the class first appears at 6.7.14.0 marked `@internal`, and is re-annotated `@experimental stableVersion:v6.8.0 feature:DOCUMENT_GENERATION_REWORK` on trunk/6.7.15.0), `documentV2.php` registers only `shopware.document_v2.provider` and `shopware.document_v2.renderer`, the v2 types are a sealed `@internal` enum of four cases, and no controller, route or flow action reaches the v2 generator. The v1 classes carry no `@deprecated` annotation at 6.7.13.0.  `[code: Checkout/Document/Renderer/AbstractDocumentRenderer.php:19-29]` `[code: Checkout/Document/Renderer/DocumentRendererRegistry.php:28-36]` `[code: Framework/DependencyInjection/CompilerPass/AutoconfigureCompilerPass.php:124-126]` `[code: Checkout/DependencyInjection/documentV2.php:62-128]`
2. The renderer alone does not make the type work: a plugin migration must insert a `document_type` row whose `technical_name` matches (plus a `document_type_translation` row per language — the translations association is `Required`) and seed a number range whose `number_range_type.technical_name` is `document_<technical_name>`, because `DocumentGenerator::generate()` resolves the name with `SELECT … FROM document_type WHERE technical_name = :technicalName` and throws `DocumentException::invalidDocumentRenderer` before the renderer registry is reached, and the number comes from `NumberRangeValueGenerator` keyed `'document_' . TYPE`. Generating from a flow additionally requires both `documentType` and `documentRangerType` in the action config.  `[code: Checkout/Document/Service/DocumentGenerator.php:119-127,233-237]` `[code: Checkout/Document/Aggregate/DocumentType/DocumentTypeDefinition.php:53-57]` `[code: Checkout/Document/Renderer/DeliveryNoteRenderer.php:171-176]` `[code: Content/Flow/Dispatching/Action/GenerateDocumentAction.php:90-93]`
3. Inside `render()` the renderer names its Twig template itself — v1 resolution is not convention-based: core renderers assign a literal path (`'@Framework/documents/delivery_note.html.twig'`) and push it onto the `RenderedDocument` with `setTemplate()`, so a plugin ships e.g. `Resources/views/documents/pro_forma_invoice.html.twig` extending `@Framework/documents/base.html.twig` (which exists in the dist) and may pick the path freely. The file body is produced by `DocumentFileRendererRegistry::render($doc)`, a second registry keyed by `RenderedDocument::getFileExtension()` and fed by `document_type.renderer` tags carrying `key="pdf"`/`key="html"`. A `document_base_config` row is optional in v1 — `DocumentConfigLoader` tolerates no match and returns an empty configuration, degrading the filename to the document number alone — though core seeds one (global + sales-channel) per type, and the admin file-type selector reads the optional `fileTypes` key from its config JSON.  `[code: Checkout/Document/Renderer/DeliveryNoteRenderer.php:54,150]` `[code: Checkout/Document/Service/DocumentFileRendererRegistry.php:21-30]` `[code: Checkout/DependencyInjection/document.xml:125,158]` `[code: Checkout/Document/Service/DocumentConfigLoader.php:57-71]` `[code: Checkout/Document/DocumentConfiguration.php:411-413]`

**Trap:** The docs clone carries two competing 6.7 answers. The Document v2 page (`AbstractDocumentType` + `AbstractDocumentDataProvider`, tags `shopware.document_v2.type` / `.provider`) describes a stack that does not exist at 6.7.13.0 — an answer built on it is wrong for this pin. The `@deprecated tag:v6.9.0` marking of v1 and the v2 public surface are announced only in the unreleased 6.7.15.0 upgrade notes.
