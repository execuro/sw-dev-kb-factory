**Query:** How do custom field sets work — entity assignment, field types and technical name — and can a custom field be written through the Store API?

**Expected answer — every fact an answer must contain:**

1. A set is created under **Settings > System > Custom fields** `[docs-only]` with an Immutable, Required technical `name`; entity assignment is its own aggregate, `custom_field_set_relation` rows carrying `set_id` + Required `entity_name`, so one set can serve several entities and a set with **no** relation row serves none — such a field is blocked on every entity for reads and can never be written. Each field's `name` and `type` are Required and Immutable, and the field name is unique **globally**, not per set (`uniq.custom_field.name` has no `set_id` component). `[code: System/CustomField/Aggregate/CustomFieldSet/CustomFieldSetDefinition.php (defineFields); System/CustomField/Aggregate/CustomFieldSetRelation/CustomFieldSetRelationDefinition.php (defineFields); System/CustomField/CustomFieldDefinition.php (defineFields); Migration/V6_3/Migration1536233300CustomField.php:32]`
2. The 6.6 administration picker offers **eleven** types — Select field, Entity select, Text field, Number field, Media field, Date/time field, Checkbox, Active switch, Text editor, Colour picker, Price field — which collapse onto eight *stored* types (`select`, `text`, `int`/`float` via the Number field's `numberType` sub-select, `datetime`, `bool`, `html`, `price`); the same eleven exist in 6.7.13.0. Eight of the sixteen `CustomFieldTypes` constants (`checkbox`, `colorpicker`, `date`, `entity`, `json`, `media`, `number`, `switch`) are unreachable from the admin and exist only for plugin/app `custom-fields.xml` and the API. In 6.6 the Twig-variable name pattern is **not** enforced — `validateBeforeWrite()` returns immediately unless the `v6.7.0.0` flag is active — so a stock 6.6 shop accepts technical names that 6.7 rejects. `[code: 6.6 Administration app/service/custom-field.service.js:17-95 and sw-settings-custom-field/snippet/en-GB.json:105-117 (ref v6.6.10.0); System/CustomField/CustomFieldTypes.php:10-25; 6.6 System/CustomField/CustomFieldService.php (validateBeforeWrite)]`
3. Read exposure, write exposure and cart exposure are **three independent columns written by three separate admin switches**: "Visible in Store API" → `store_api_aware` (`StructEncoder` strips every field with `store_api_aware = 0` from Store API responses), "Modifiable via Store API" → `allow_customer_write` (`StoreApiCustomFieldMapper`'s SQL whitelist), "Available in shopping carts" → `allow_cart_expose` (rendered only for product sets). Writes exist only on the four callers of that mapper — register (customer + addresses), change-profile, upsert-address, newsletter-subscribe — i.e. on `customer`, `customer_address` and `newsletter_recipient` only; any other route ignores a `customFields` payload. In **6.6** a change-profile or upsert-address request whose `customFields` contain only non-whitelisted keys produces an empty map that is written through as `'{}'`, wiping *all* stored custom fields on that record; 6.7.13.0 guards this with `if ($customerData['customFields'] === []) { unset(...); }`. A non-empty mapped subset is patched via `JSON_SET`, so non-whitelisted stored keys survive. `[code: 6.6 Administration sw-custom-field-detail.html.twig:56-90 (ref v6.6.10.0); System/SalesChannel/Api/StructEncoder.php:378; System/SalesChannel/StoreApiCustomFieldMapper.php:56-70; 6.6 Checkout/Customer/SalesChannel/ChangeCustomerProfileRoute.php:106-111; Framework/DataAbstractionLayer/FieldSerializer/CustomFieldsSerializer.php:49,63]`

**Official reference URL:** https://docs.shopware.com/en/shopware-6-en/settings/custom-fields
